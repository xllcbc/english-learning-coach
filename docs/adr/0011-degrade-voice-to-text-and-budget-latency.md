# 语音链路降级到文本，并以回合制控制延迟

## 背景

Speaking Practice 依赖 STT 与 TTS 供应商，可能失败、超时或高延迟。若语音一失败整段不可用，会拖累已经可用的文本对话能力。需要明确降级策略与延迟边界，并且让语音链路在没有麦克风的情况下也能被测试。

## 决策

1. **语音是文字之上的适配器。** STT 失败或超时，降级为文字输入，进入同一回合、同一核心；TTS 失败则显示文字回答。
2. **延迟预算。** 从说完到开始播放的 p95 目标约 2.5 秒；超预算时显示「思考中」态，而不是静默等待。
3. **barge-in。** 学习者开始新语音时，通道层取消正在播放的 TTS。
4. **可测。** SpeechModel 藏在 seam 之后并提供确定性 mock（固定转写、固定音频字节），无麦克风也能测试整条链路。
5. **第一版回合制。** 使用 WebSocket + Whisper STT + OpenAI TTS；Realtime 双工列为后续升级，不进入第一版。

## 与既有 ADR 的关系

- **ADR-0003（使用 Spring AI 接入模型）**：沿用。STT/TTS 复用 Spring AI 的音频能力与既有 API-key 条件。
- **ADR-0009（回合制核心 + 通道适配器）**：本 ADR 是其在语音通道上的具体化。

## 后果

- 语音不可用时不阻塞学习；降级路径必须被测试覆盖。
- 回合制语音延迟高于双工；这是第一版为可测性与范围做的取舍。
